# ADR-001 — Единый реестр курсов (устранение дублирования платных course ID)

Статус: **Proposed — ожидает утверждения владельца. НЕ реализовано; код не
менялся.**
Дата: 2026-08-05
Расположение: папка `decisions/` задана владельцем (инструкция 2026-08-05);
после создания `25_DECISIONS.md` ADR регистрируется там (`CLAUDE.md` §3).
Все факты — из `lalianamen/llicena@main` на 2026-08-05; непроверяемое — UNKNOWN.

## 1. Текущая архитектура (контекст)

Продукт — статический фронтенд (GitHub Pages, ветка `main`) + Supabase
(Postgres/RLS, Edge Functions) + Stripe (`02_ARCHITECTURE.md`). Курс — это
строка каталога (`js/catalog/<state>.js`) с id, который связывает: банк
вопросов, строку доступа `user_courses`, платёж Stripe и триал. Признак
«платный» НЕ хранится в каталоге — он существует только в виде
захардкоженных списков course_id в клиенте, Edge Function и SQL. Цена одна
для всех платных курсов: `PRICE_CENTS = 2000`
(`supabase/functions/stripe-checkout/index.ts:19`).

## 3. Подтверждённые случаи рассинхронизации

1. **Продакшен-инцидент 2026-08-04** (шапка `check-paid-sync.js`): банки
   `c33-painting` и `az-sre` добавили только в клиентские списки →
   checkout падал («Не удалось начать оплату»), `start_trial` возвращал
   `not_paid_course`, а RLS-политика **позволяла любому самовыдать новые
   платные банки бесплатно** (её not-in список о них не знал). После этого
   написан чекер.
2. **`subscriptions-schema.sql` (2026-07-18) пропустил `c27-landscaping`**
   в бета-экспирации — без правки A2 в `stripe-payments.sql` строки c27
   «остались бы бесплатными навсегда» (комментарий A2).
3. **Поздне-бетовые строки** получили `expires_at NULL` и не гасились бы
   кроном — закрыто B2 (комментарий B2).
4. **Действующие расхождения комментариев/списков**: «nine PAID banks» в

## 4. Предлагаемая единая модель `courses`

Новая таблица Postgres — единственный источник истины о платности:

```sql
create table public.courses (
  course_id   text primary key,          -- тот же id, что в каталоге
  is_paid     boolean not null default false,
  title_en    text not null,             -- имя для Stripe-чекаута/квитанций
  price_cents integer,                   -- null = глобальный дефолт 2000
  active      boolean not null default true
);
-- RLS: публичное чтение (is_paid и так виден в UI), запись — только service role.
```

Поля `title_en`/`price_cents` покрывают то, что сегодня дублирует карта
`PAID` чекаута; `active` — задел под запуск `la-business-law` без правки
пяти списков. Состав колонок — предложение; финализирует владелец.

## 5. Варианты реализации

**A. Таблица `courses` в Postgres (сервер — читает таблицу; клиент — флаг в каталоге).**
RLS-политики и `start_trial` проверяют подзапросом; `stripe-checkout`
читает строку курса; клиентские `PAID_SUBS`/`PAID_COURSES` заменяются
флагом `paid:true` в `js/catalog/<state>.js` (данные и так публичные);
`check-paid-sync.js` сравнивает флаги каталога с seed-файлом таблицы.

**B. Только репозиторий: флаг `paid:true` в каталоге + генератор.**
Каталог — источник истины; скрипт генерирует SQL (политики, allowlist)
и секцию `PAID` функции; серверные артефакты остаются захардкоженными,
но производными. Без изменения рантайма БД.

**C. Статус-кво + расширение чекера.**
Добавить в `check-paid-sync.js` список №7 (+ проверку счётчиков в
комментариях). Дублирование остаётся, но весь его периметр под ошибкой
verify.js.

## 6. Рекомендуемый вариант

**A**, с элементом B для клиента (флаг в каталоге вместо клиентских
Set-списков). Основание из фактов проекта: все три точки НАРУШЕНИЯ в
инциденте 2026-08-04 — серверные или серверно-зависимые (checkout, trial,
RLS); таблица делает их производными от одной строки INSERT. Вариант B
оставляет ручной шаг «прогнать генератор и раскатить SQL» — тот же класс
ошибки «забыли шаг»; вариант C не убирает долг (7+ мест остаются).
Чекер при варианте A сохраняется на переходный период как страховка.

## 8. План миграции без остановки production

Каждый шаг обратно-совместим; порядок — сервер сначала:

0. Предусловие: подтвердить фактическое состояние живой БД (применён ли
   SECTION B) — сейчас UNKNOWN; план предполагает «применён».
1. Создать таблицу + seed (аддитивно; ни один существующий путь её ещё не
   читает — ноль влияния).
2. Задеплоить новую `start_trial()` (мгновенная замена; контракт возвратов
   не меняется).
3. Одной транзакцией пересоздать две RLS-политики на подзапросную форму
   (шаблон цикла по `pg_policies` уже есть в SECTION B).
4. Задеплоить новый `stripe-checkout` (чтение таблицы).
5. Прогнать приёмочные проверки серверного слоя (см. §11) — старый клиент
   в этот момент полностью работоспособен: его Set-списки совпадают с seed.
6. Выкатить клиентский коммит (флаги каталога + производные списки) с
   бампами `?v=`; SW network-first отдаёт свежие файлы онлайн-пользователям
   сразу.
7. Обновить чекер и генератор CSV; удалить мёртвые списки; обновить доки.

## 9. Риски

- Живое состояние БД UNKNOWN (шаг 0): если SECTION B не применялся,
  пересоздание политик изменит поведение сильнее, чем описано.
- Пропущенная строка seed: у RLS-подзапроса отказ «мягкий» в опасную
  сторону — курс без строки `is_paid` считается бесплатным (self-grant).
  Митигация: переходный чекер сравнивает seed с флагами каталога, а до
  удаления — со старыми списками; приёмочный тест «нет строки → нет
  самовыдачи» обязателен.
- Подзапрос в RLS-политике исполняется на каждую INSERT/UPDATE
  `user_courses`; масштаб проекта мал (сотни строк), но замеров нет —
  UNKNOWN.
- Окно между шагами 3 и 4: политики уже табличные, checkout ещё со старой
  картой — списки идентичны по seed, дрейфа нет; риск только при
  одновременном добавлении нового курса во время миграции (не делать).
- Кэш клиентов офлайн (SW отдаёт старую версию до первого онлайн-захода) —
  старые Set-списки остаются корректными, т.к. состав курсов в миграции не
  меняется.

## 10. Rollback-план

Каждый шаг откатывается независимо, историческими файлами репозитория
(append-only, `26_CHANGELOG.md`):

- RLS: повторно выполнить SECTION B из `supabase/sql/stripe-payments.sql`
  (идемпотентен — сам дропает политики циклом и создаёт списочные версии).
- `start_trial`: повторно выполнить `supabase/sql/trial-3day.sql`
  (`create or replace`).
- `stripe-checkout`: `supabase functions deploy` предыдущей версии из git.
- Клиент: revert клиентского коммита + бамп `?v=`.
- Таблица `courses` при откате может остаться (её никто не читает) —
  удаление не требуется.

## 11. Тесты и критерии приёмки

Автоматические (`node scripts/verify.js` зелёный до и после каждого шага):
обновлённый `check-paid-sync.js` (seed ↔ каталог ↔ переходно старые
списки), `check-banks.js`, `check-course-ref.js`, `node --check`.

Ручные серверные (шаг 5): для КАЖДОГО из 14 course_id — `start_trial` даёт
`ok`/`trial_used` как раньше; upsert платного id под authenticated →
отказ RLS; upsert бесплатного id → успех; `stripe-checkout` на платный id
→ `{url}` с верным именем курса, на бесплатный/несуществующий → 400, на
активную подписку → 409; тестовая покупка через `?paidtest=1`-путь
(механизм уже есть, `js/app-cabinet.js:634–638`) → вебхук выдаёт доступ.

Ручные клиентские (шаг 6, чек-лист `CLAUDE.md` осн. репо): рендер кабинета
desktop+360px, EN+RU; ветки Activate/Trial/Subscribe на трёх типах курсов;
плеер: платный неактивный → пейвол, платный активный → банк из БД.

Критерий закрытия долга: **добавление нового платного курса = 1 строка
seed + 1 строка каталога**, всё остальное подхватывается без правок;
негативный тест «курс без seed-строки не самовыдаётся» проходит.
