# CLAUDE.md — постоянная инструкция по проекту LICENA

Этот файл — главная постоянная инструкция для любой AI-сессии (Claude),
работающей над проектом LICENA. Следовать ему без исключений.

## 1. Роль

- Роль Claude в проекте двойная:
  1. **разработка проекта LICENA** (сайт licena.us, основной репозиторий
     `https://github.com/lalianamen/llicena`);
  2. **подготовка и поддержание фактической документации** по проекту.
- Репозиторий `https://github.com/lalianamen/licena-docs` (этот репозиторий) —
  **единая база знаний проекта** и единственное место хранения всей
  документации для аудита. Документация нигде больше не ведётся.
- При работе с кодом в основном репозитории дополнительно действует его
  собственный `CLAUDE.md` (правила Karpathy, agent lanes, правила банков
  вопросов). При противоречии приоритет у настоящего файла.

## 2. Правдивость данных — главное правило

- **Запрещено придумывать отсутствующие данные.** Ни домыслов, ни
  экстраполяций, ни «примерных» цифр, ни правдоподобных заполнителей.
- Каждый факт в документации должен прослеживаться до первоисточника:
  файла в основном репозитории LICENA (код, SQL, `docs/**`, git-история)
  или явного сообщения владельца. Факты берутся из текущего состояния
  репозитория, а не по памяти.
- **Если информации нет или её нельзя проверить — писать ровно `UNKNOWN`**
  (при необходимости с уточнением: `UNKNOWN — в репозитории нет данных о …`).
- Пустые шаблоны запрещены: документ либо содержит реальные данные
  (с `UNKNOWN` на местах пробелов), либо не создаётся вовсе.

## 3. Синхронизация кода и документации

- **После каждого изменения кода** в основном репозитории — в том же рабочем
  цикле обновить затронутые документы в licena-docs.
- **После каждого значимого изменения** обязательно обновлять:
  `26_CHANGELOG.md`, `27_ROADMAP.md`, `28_AI_CONTEXT.md`, `25_DECISIONS.md`,
  `18_DEPENDENCIES.md` и `RELEASE_SUMMARY.md`.
  Значимое изменение — это: новая функциональность; изменение схемы БД, API,
  Edge Functions, платежей, безопасности, зависимостей, структуры контента,
  SEO-механики или деплой-процесса; выпуск нового банка/курса.
- **Крупные архитектурные изменения сначала оформляются как RFC или ADR**
  (файл в папке `rfc/`, ссылка регистрируется в `25_DECISIONS.md`) и только
  после этого реализуются.
- **Историю решений и изменений удалять запрещено.** `26_CHANGELOG.md`,
  `25_DECISIONS.md`, `rfc/` и прочие журналы — только пополняются
  (append-only). Ошибочная запись помечается отменённой новой записью, но не
  стирается. Force-push и переписывание git-истории в licena-docs запрещены.

## 4. Структура базы знаний (файлы аудита)

Создать и поддерживать файлы аудита с `01_PROJECT_OVERVIEW.md` по
`29_BUSINESS_FRAMEWORK.md` плюс `30_CTO_REPORT.md`. Имена 01, 29 и 30 заданы
владельцем; канонические имена 02–28 закреплены настоящим файлом:

- `README.md` — оглавление базы знаний;
- `audit/INDEX.md` — реестр всех документов: статус заполнения, дата последней
  проверки, уровень достоверности;
- `audit/COVERAGE.md` — карта покрытия: какие части основного проекта уже
  задокументированы, какие нет.
  Оба файла обновляются при каждом изменении состава или статуса документов.

## 5. Что обязательно фиксировать

Документация обязана покрывать: архитектуру, базу данных, API, функции,
безопасность, производительность, технический долг, зависимости, решения,
риски, SEO, UX, аналитику, метрики и историю изменений.

## 6. Разделение ролей аудита

- Claude ведёт **фактическую** документацию: что есть в проекте и как оно
  устроено. Источник — только основной репозиторий LICENA и сообщения
  владельца.
- **Бизнес-аудит и выставление оценок Claude не проводит** — это делает
  ChatGPT (в том числе в `30_CTO_REPORT.md`).
- `29_BUSINESS_FRAMEWORK.md` содержит только фактические бизнес-данные,
  без выводов и рекомендаций.

## 7. Публичность и безопасность

- licena-docs — **публичный** репозиторий. Запрещено помещать в него секреты:
  API-ключи, токены, пароли, содержимое `.env`, персональные данные
  пользователей. Вместо значения указывается место хранения (например,
  «секрет задан в Supabase Edge Function secrets») либо `UNKNOWN`.

## 8. Рабочий процесс

- Язык документации — русский; имена файлов, технические термины,
  идентификаторы и цитаты кода — на английском. Маркер отсутствия данных —
  всегда `UNKNOWN`.
- Работать в ветке, назначенной для текущей сессии; коммиты — с ясными
  описательными сообщениями; push — после завершения логического блока работы.
- В каждом документе указывать дату последней сверки с основным репозиторием
  (строка вида `Последняя сверка: YYYY-MM-DD`).

## 9. Стандарт документа для независимого аудита (действует с 2026-08-05)

Документация читается не только разработчиками, но и независимым аудитором
(ChatGPT). Каждый документ базы знаний обязан соответствовать правилам:

1. Только **проверяемые факты**.
2. **Каждое утверждение** имеет ссылку на источник внутри проекта: файл,
   директорию, миграцию, модуль, ветку или коммит основного репозитория.
3. Отсутствующая информация — ровно `UNKNOWN`.
4. Никаких выводов, оценок и предложений улучшений.
5. Никаких общих фраз — только конкретные сведения (имена, числа, пути, даты).
6. Обязательный раздел **«Source References»**: полный список файлов проекта,
   из которых получена информация документа.
7. Обязательный раздел **«Verification Status»** с одним из уровней:
   - **Verified** — каждое утверждение проверено чтением названного источника;
   - **Partially Verified** — часть данных помечена `UNKNOWN` и/или взята из
     описаний (комментариев, документов), не перепроверенных по реализации —
     такие места названы явно;
   - **Unknown** — документ не проходил проверку.
8. Если сведение выводится из нескольких файлов — перечисляются **все**.
9. `audit/INDEX.md` (реестр документов) и `audit/COVERAGE.md` (карта покрытия)
   обновляются при каждом создании или изменении документа.
